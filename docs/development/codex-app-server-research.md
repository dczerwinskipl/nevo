# Codex app-server protocol research

This note preserves concise discovery evidence. It is not a raw terminal transcript and
does not promote one observed payload shape into a cross-version protocol guarantee.

## Verification environment and procedure

- **Date:** 2026-08-22
- **Codex CLI:** `0.149.0`
- **Platform:** Windows
- **Process command:** `codex app-server --listen stdio://`
- **Request sequence:** `initialize` -> `initialized` -> `thread/start` -> `turn/start`

The stdio JSONL connection, initialization, fresh thread creation, and turn start all
completed successfully against the locally installed executable.

## Verified observations

### Initialization

The successful initialization result included `codexHome`, platform information, and
`userAgent`.

### Thread identity and initial state

A fresh `thread/start` returned an authoritative `thread.id`, an initial `idle` status,
cwd, model/provider information, and approval/sandbox information. Its `sessionId`
happened to equal `thread.id` in this run.

The equality is an observation only. Nevo's identity contract remains `thread.id` as the
sole `providerSessionId`; `sessionId` is provider metadata and must not become an alias or
fallback identity.

### Turn and item lifecycle

`turn/start` returned immediately with a Codex `turn.id` and `inProgress` status. The
observed stream then included:

1. `thread/status/changed` to `active`;
2. `turn/started`;
3. `item/started` for the user message;
4. `item/completed` for the user message.

The user-message item lifecycle precedes assistant output. It is not assistant text, a
tool lifecycle, or evidence that the turn completed.

### Generated assistant-output shape

The generated 0.149.0 item schema represents `agentMessage.phase` as optional, with
wire values `commentary` and `final_answer`. The agent-message delta notification carries
`itemId` and `delta`, not phase, so phase-aware consumers must correlate deltas to the
started/completed item. Reasoning remains a separate item with summary/content and
separate summary/raw-text delta notifications. These generated shapes agree with the
official app-server documentation; the compact verifier baseline locks the consumed
optional phase semantics.

### Provider-global notifications

The process emitted well-formed notifications outside an active turn, including:

- `remoteControl/status/changed`;
- `mcpServer/startupStatus/updated`;
- `skills/changed`.

A narrow Nevo client must not require every notification to correlate to an active
thread/turn. Well-formed notifications outside the consumed inventory can be ignored
without failing active work.

### Envelope tolerance

The manual client included `"jsonrpc":"2.0"` and Codex accepted it. Observed server
responses and notifications omitted that member. Nevo should emit the smaller documented
envelope and should not require `jsonrpc`; however, an otherwise well-formed incoming
envelope is not corrupt merely because it includes a harmless `jsonrpc` member, unless
the generated schema for the selected Codex version explicitly requires rejection.

## Implications for Nevo

- Keep `thread.id` as the only persisted Codex provider session identity.
- Correlate consumed work through explicit thread, turn, item, request, and response IDs.
- Distinguish user-message items before mapping assistant or tool events.
- Ignore unrelated well-formed provider-global notifications; fail closed only for
  malformed envelopes, broken correlation of consumed work, or invalid consumed shapes.
- Send minimal documented request envelopes while parsing the observed optional
  `jsonrpc` member tolerantly.
- Retain generated-schema verification: this smoke test proves one executable/version
  path works, not that every consumed union or future Codex version has the same shape.

## Observation versus contract

The facts above are verified for Codex CLI `0.149.0` on Windows. The durable protocol
contract still comes from the official
[Codex app-server documentation](https://developers.openai.com/codex/app-server) and the
schemas generated by the exact executable selected at implementation/runtime. Where a
future generated schema contradicts this note, record the new versioned observation and
resolve the compatibility decision explicitly rather than silently preserving the old
assumption.
