# Owner decisions — nevo-ai-process-continuity-and-hardening

## D1: Fingerprint scope (semantic vs. operational)

- **Question:** The review fingerprint (`tools/specs.mjs fingerprint`) hashes `change.yaml` byte-for-byte, so one task's status transition invalidates the review fingerprint of every other task in the same change. How should semantic content be separated from operational state for fingerprinting purposes?
- **Options considered:** (A) Strip status fields before hashing (parse, exclude `status` at change and task level, hash the rest) | (B) Split `change.yaml` into a semantic file and a separate operational-state file | (C) Keep as-is, document the limitation only
- **Decision:** (A) Strip status fields before hashing.
- **Rationale:** Smallest schema change, fixes the confirmed bug, no file split, lowest migration cost for the in-flight `nevo-documentation-architecture` change.
- **Consequences:** `computeSpecFingerprint` must parse `change.yaml` (and area/task front matter) and exclude `status` (change-level and per-task) — and only `status` — from the hashed content, rather than hashing raw file bytes. No new file is introduced. Existing stored `spec_fingerprint` values in any `reviews/*.md` become stale the first time this change ships (expected — see migration task) and must be regenerated by re-running the affected review.
- **Date:** 2026-08-04
- **Affected artifacts:** `tasks/01-state-and-fingerprint-semantics.md`, `tasks/09-finalization-hardening-and-migration.md`

## D2: Auto-continue scope

- **Question:** How far may the AI proceed automatically through workflow transitions before it must stop for a fresh owner confirmation?
- **Options considered:** (A) Conservative — only recoverable-error repair/retry is automatic | (B) Moderate — adds inline "offer next transition" after a successful command, but implementation-start/merge/finalize keep their own confirmation | (C) Expansive — an owner-selected batch of approved tasks may run end-to-end (implement → self-check → next task) with one confirmation at the start and one gating review at the end
- **Decision:** (C) Expansive.
- **Rationale:** Owner explicitly chose the batch model over the moderate option to minimize per-task interruption for small, low-risk tasks.
- **Consequences:** The controller may execute an entire owner-authorized batch (`task-start` → implement → self-check → `complete` → next task) without a fresh confirmation per task, but must still stop immediately at: an owner-approval-gate decision (per `AGENTS.md`), an unsafe/ambiguous recovery, a requested checkpoint, the end of the requested batch, or a task whose scope/classification has changed since approval. The gating batch review at the end is not skippable — see D4 and Area `batch-execution-and-gating-review`. This does not relax `spec-approve`'s own three-outcome rule (see D3) — a task must already be `approved` before it can enter a batch run.
- **Date:** 2026-08-04
- **Affected artifacts:** `tasks/03-resume-and-continue-controller.md`, `tasks/04-conversational-approval-ergonomics.md`, `tasks/08-batch-execution-and-gating-review.md`

## D3: Approve + start combined confirmation

- **Question:** Should approving a task and starting its implementation ever be authorized in a single owner confirmation, or must they always be two separate turns?
- **Options considered:** (A) Keep separate, two turns always | (B) Allow one combined confirmation that authorizes both, while `approve` and `start` remain two separate, auditable CLI transitions
- **Decision:** (B), with explicit conditions: approval and start remain separate, auditable CLI transitions under the hood. After `approve` succeeds, the controller re-inspects state (branch, working tree, dependency status) and executes `start` only if `start`'s own guards still pass at that moment — it does not blindly chain. A failure in `start` must not roll back the just-completed `approve`, and must not silently re-attempt `approve` — the task stays `approved`, `start` failure is reported, and the owner (or a subsequent `/nevo-ai:task-start`) drives the retry.
- **Rationale:** Owner-specified — preserves the auditability of two distinct CLI calls while removing a redundant conversational round-trip; the re-guard-check and no-rollback rule prevent the combined confirmation from silently masking a state change between the two calls (e.g. dirty worktree introduced between approve and start).
- **Consequences:** `spec-approve`'s three-outcome rule is extended, not replaced: a fourth outcome ("approve and start") becomes available, but only ever as an explicit, separately-labeled menu choice — never the default, never inferred from context. `handleStart`'s existing pre-flight checks (working-tree-clean, transition validity, `depsSatisfied`) are the "guards" re-checked after `approve`; no new guard logic is invented for this path beyond what `start` already does standalone.
- **Date:** 2026-08-04
- **Affected artifacts:** `tasks/04-conversational-approval-ergonomics.md`

## D4: Batch execution and mechanical task type — build now

- **Question:** Should batch execution (sequential multi-task runs with one gating review at the end) and a narrow auto-approvable "mechanical task" type be designed and built in this change, or designed now and deferred to a follow-up change?
- **Options considered:** (A) Design only, defer build | (B) Build both now | (C) Build batch execution now, drop the mechanical task type as a non-goal
- **Decision:** (B) Build both now.
- **Rationale:** Owner explicitly chose full scope over deferral.
- **Consequences:** This change's task list includes both `tasks/07-mechanical-task-type.md` and `tasks/08-batch-execution-and-gating-review.md` as implementable units, not just design sections in `overview.md`. This increases the change's size and blast radius (already classified **A**); no change to classification results from this decision since the change was already Architectural.
