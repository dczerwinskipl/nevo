# Owner decisions — nevo-ai-process-continuity-and-hardening

## D1: Fingerprint scope (semantic vs. operational)

- **Question:** The review fingerprint (`tools/specs.mjs fingerprint`) hashes `change.yaml` byte-for-byte, so one task's status transition invalidates the review fingerprint of every other task in the same change. How should semantic content be separated from operational state for fingerprinting purposes?
- **Options considered:** (A) Strip status fields before hashing (parse, exclude `status` at change and task level, hash the rest) | (B) Split `change.yaml` into a semantic file and a separate operational-state file | (C) Keep as-is, document the limitation only
- **Decision:** (A) Strip status fields before hashing.
- **Rationale:** Smallest schema change, fixes the confirmed bug, no file split, lowest migration cost for the in-flight `nevo-documentation-architecture` change.
- **Consequences:** `computeSpecFingerprint` must parse `change.yaml` (and area/task front matter) and exclude `status` (change-level and per-task) — and only `status` — from the hashed content, rather than hashing raw file bytes. No new file is introduced. Existing stored `spec_fingerprint` values in any `reviews/*.md` become stale the first time this change ships (expected — see migration task) and must be regenerated by re-running the affected review.
- **Date:** 2026-08-04
- **Affected artifacts:** `tasks/01-state-and-fingerprint-semantics.md`, `tasks/09-finalization-hardening-and-migration.md`
- **Refined by:** D7 (2026-08-04 refinement pass) — the exclude-`status` mechanism is still correct but was too coarse (change-wide, single fingerprint); D7 generalizes it into a three-tier semantic-projection model. This entry is kept for the audit trail; D7 is authoritative on granularity.

## D2: Auto-continue scope

- **Question:** How far may the AI proceed automatically through workflow transitions before it must stop for a fresh owner confirmation?
- **Options considered:** (A) Conservative — only recoverable-error repair/retry is automatic | (B) Moderate — adds inline "offer next transition" after a successful command, but implementation-start/merge/finalize keep their own confirmation | (C) Expansive — an owner-selected batch of approved tasks may run end-to-end (implement → self-check → next task) with one confirmation at the start and one gating review at the end
- **Decision:** (C) Expansive.
- **Rationale:** Owner explicitly chose the batch model over the moderate option to minimize per-task interruption for small, low-risk tasks.
- **Consequences:** The controller may execute an entire owner-authorized batch (`task-start` → implement → self-check → `complete` → next task) without a fresh confirmation per task, but must still stop immediately at: an owner-approval-gate decision (per `AGENTS.md`), an unsafe/ambiguous recovery, a requested checkpoint, the end of the requested batch, or a task whose scope/classification has changed since approval. The gating batch review at the end is not skippable — see D4 and Area `batch-execution-and-gating-review`. This does not relax `spec-approve`'s own three-outcome rule (see D3) — a task must already be `approved` before it can enter a batch run.
- **Date:** 2026-08-04
- **Affected artifacts:** `tasks/03-resume-and-continue-controller.md`, `tasks/04-conversational-approval-ergonomics.md`, `tasks/08-batch-execution-and-gating-review.md`
- **Refined by:** D8 (execution suspension is now the mechanism that stops expansive continuation at an unsafe/ambiguous recovery or owner-decision point — see D8; the stop conditions listed here are unchanged, only how a stop is represented in state changed).

## D3: Approve + start combined confirmation

- **Question:** Should approving a task and starting its implementation ever be authorized in a single owner confirmation, or must they always be two separate turns?
- **Options considered:** (A) Keep separate, two turns always | (B) Allow one combined confirmation that authorizes both, while `approve` and `start` remain two separate, auditable CLI transitions
- **Decision:** (B), with explicit conditions: approval and start remain separate, auditable CLI transitions under the hood. After `approve` succeeds, the controller re-inspects state (branch, working tree, dependency status) and executes `start` only if `start`'s own guards still pass at that moment — it does not blindly chain. A failure in `start` must not roll back the just-completed `approve`, and must not silently re-attempt `approve` — the task stays `approved`, `start` failure is reported, and the owner (or a subsequent `/nevo-ai:task-start`) drives the retry.
- **Rationale:** Owner-specified — preserves the auditability of two distinct CLI calls while removing a redundant conversational round-trip; the re-guard-check and no-rollback rule prevent the combined confirmation from silently masking a state change between the two calls (e.g. dirty worktree introduced between approve and start).
- **Consequences:** `spec-approve`'s three-outcome rule is extended, not replaced: a fourth outcome ("approve and start") becomes available, but only ever as an explicit, separately-labeled menu choice — never the default, never inferred from context. `handleStart`'s existing pre-flight checks (working-tree-clean, transition validity, `depsSatisfied`) are the "guards" re-checked after `approve`; no new guard logic is invented for this path beyond what `start` already does standalone.
- **Date:** 2026-08-04
- **Affected artifacts:** `tasks/04-conversational-approval-ergonomics.md`

## D7: Fingerprint granularity — three-tier semantic model

- **Question:** A single change-wide semantic fingerprint (D1) still causes expensive invalidation when the draft gains a mechanical task, a resolver task, a new dependency, a discovered follow-up, an unrelated task, or a task-local context correction — reproducing the same token/ceremony cost under a different trigger. What granularity should the fingerprint model actually use?
- **Options considered:** presented as a required model, not a menu — (A) keep one change-wide fingerprint (status-excluded, per D1) | (B) three-tier model: change-level, task-level, implementation-review fingerprints, each a canonical semantic projection with an explicit invalidation matrix
- **Decision:** (B) Three-tier model.
- **Rationale:** Owner-supplied refinement — (A) was confirmed to reproduce the original problem class under new triggers; a canonical per-tier projection (not a whole-file hash with an exclusion list) is required so invalidation can be reasoned about per change.
- **Consequences:** `computeSpecFingerprint` is replaced by three functions: `computeChangeFingerprint` (change scope, shared constraints, owner decisions, change-level acceptance criteria, task graph, cross-task invariants, shared context rules), `computeTaskFingerprint(taskId)` (that task's definition, acceptance criteria, `allowed_paths`/`consequential_paths`/`forbidden_paths`, context, relevant dependencies, referenced owner decisions, shared constraints it actually uses), and `computeImplementationFingerprint(taskId)` (task semantic fingerprint + reviewed diff/revision + evidence references). A review file records the fingerprint(s) relevant to its own scope — a spec review records `change_fingerprint`; a task review records `task_fingerprint` and, once implementation exists, `implementation_fingerprint`. See `overview.md` § "Proposed architecture" → "State model" for the full invalidation matrix.
- **Date:** 2026-08-04 (refinement pass)
- **Affected artifacts:** `tasks/01-state-and-fingerprint-semantics.md`, `overview.md`

## D8: Lifecycle status vs. execution suspension

- **Question:** The original draft proposed making `blocked`/`needs-decision` reachable task statuses for recoverable stops, but defined no complete return-path transition model for them — risking a new zombie-state class (a task recorded as "blocked" with no deterministic way back). Should recoverable stops be represented as lifecycle statuses, or as separate state?
- **Options considered:** presented as a required model — (A) keep `blocked`/`needs-decision` as real lifecycle statuses with a fully defined inbound/outbound transition table for each | (B) keep the stable task lifecycle status (`draft`/`approved`/`in-implementation`/.../terminal) completely unchanged, and persist a separate, orthogonal `execution.suspension` structure that records *why the last action stopped*, independent of the task's real lifecycle position
- **Decision:** (B).
- **Rationale:** Owner-supplied refinement — (B) avoids inventing new transition semantics for `TRANSITIONS` entirely (no change to `lifecycle.mjs:29-34` is needed), and makes "what stable state do I return to" trivially answerable: it's whatever `status` already says, since `status` was never overwritten by the stop.
- **Consequences:** `blocked`/`needs-decision` are **not** wired up as reachable in this change after all (this reverses part of D6/task 01's original scope) — they remain in the vocabulary, unreachable, exactly as found in discovery, and this refinement does not touch them further. Every task in `change.yaml` gains an optional `execution: { suspension: {...} }` block, persisted, excluded from every fingerprint tier (operational, like `status`). See `overview.md` § "Proposed architecture" → "Recovery model" for the full suspension schema and clearing rules.
- **Date:** 2026-08-04 (refinement pass)
- **Affected artifacts:** `tasks/01-state-and-fingerprint-semantics.md`, `tasks/02-recovery-classification-and-machine-readable-errors.md`, `overview.md`

## D9: Post-merge failure model

- **Question:** The original design let a failed post-merge check write a follow-up entry into a change that may already be merged, archived, and removed from `specs/active/`, with its branch deleted — mutating an already-finalized artifact with no commit path. What should actually happen on a post-merge verification failure?
- **Options considered:** (A) verify before destructive cleanup — merge, update local `main`, run the quick post-merge check, and only *then* delete the branch and finish cleanup; on failure, report the failed-finalization state and preserve the branch as the recovery anchor | (B) a post-merge failure creates a new small repair change/task on a new branch | (C) report-only — print the final SHA, the failed check, and the exact recovery command, without writing anything
- **Decision:** (A).
- **Rationale:** This is a technical sequencing decision inside an already-approved mechanism (D6's post-merge check), not a fresh scope/architecture gate — decided here per the refinement request's explicit instruction not to defer it to implementation, and because it is the only option consistent with the required regression scenario "branch cleanup does not occur before the chosen post-merge safety boundary": only (A) has a cleanup boundary to test. Flagged clearly for the owner to override in review if a different behavior is actually wanted.
- **Consequences:** `spec-finalize`'s merge step no longer passes branch deletion in the same call as the squash-merge — `gh pr merge --squash` without `--delete-branch`, then a separate, explicit branch-deletion step gated on the post-merge check passing. On failure: report the merged PR's SHA, the failed check and its output, and the exact recovery command (e.g. re-run `node tools/specs.mjs check`/`docs.mjs check` after manually fixing on the still-existing branch) — no follow-up ledger entry is written into the archived change, since that would be exactly the "mutate a finalized artifact with no commit path" problem this decision exists to avoid.
- **Date:** 2026-08-04 (refinement pass)
- **Affected artifacts:** `tasks/09-finalization-hardening-and-migration.md`, `overview.md`

## D10: Batch progress persistence — derived, not duplicated

- **Question:** The original design proposed a `.batch-state.json` tracking completed tasks alongside `change.yaml`'s own task statuses — two sources of truth that can disagree after an interrupted write. What should batch progress state actually persist?
- **Options considered:** presented as a required/preferred model — (A) keep both, define write order/atomicity/reconciliation/crash-recovery/authoritative-source-on-conflict | (B) persist only batch *intent* (which tasks were requested, in what order, from what revision, under what review/checkpoint policy, plus declared temporary-inconsistency pairs) and derive completed/current/next/failed entirely from `change.yaml` task status + `execution.suspension` (D8)
- **Decision:** (B).
- **Rationale:** Simpler, no dual-write/reconciliation logic to build or test, and task status is already the authoritative record of task progress — recording it twice adds a failure mode without adding information.
- **Consequences:** The persisted batch file (see task 08) holds exactly: `change`, `requestedTasks`, `orderedTasks`, `startRevision`, `reviewMode`, `checkpointPolicy`, `temporaryInconsistencies` — no `completed`/`current`/`failed` fields. `deriveStage`/the resume controller (D8/task 03) computes those by reading task status and suspension directly.
- **Date:** 2026-08-04 (refinement pass)
- **Affected artifacts:** `tasks/08-batch-execution-and-gating-review.md`, `overview.md`

## D11: Batch risk classification — evidence-based, not path-touch-based

- **Question:** The original risk rule required a full `task-review` for any batched task touching `src/**`, `tests/**`, or `consequential_paths` — which is nearly every code task, defeating batch mode's token-saving purpose. What should actually trigger a full review inside a batch?
- **Options considered:** presented as a required model — keep the path-touch trigger | replace it with explicit, evidence-based risk signals
- **Decision:** Evidence-based signals: a task-declared `review: required`, public-API/compatibility impact, security/authorization/data-safety impact, migration or destructive-persistence behavior, an `owner-decision:`-tagged acceptance criterion, scope expansion during implementation, an unresolved or failed self-check, missing automated verification, unexpected files outside the approved path model, implementation divergence from the approved design, or an owner-flagged high-risk task.
- **Rationale:** Matches the actual purpose of batch mode (save review ceremony for small, low-risk tasks) instead of defeating it by treating "touches code at all" as risky.
- **Consequences:** A small code task with approved scope, no public-contract change, complete automated verification, no new decision, and no unresolved findings is eligible for lightweight self-check plus the end-of-batch gating review only — no mandatory full `task-review`.
- **Date:** 2026-08-04 (refinement pass)
- **Affected artifacts:** `areas/batch-execution-and-gating-review.md`, `tasks/08-batch-execution-and-gating-review.md`

## D12: Context routing contract — stable and machine-readable

- **Question:** The original design expected deterministic parsing of `docs/ai/task-routing.md`/`docs/ai/change-impact-map.md` as free-form Markdown prose, which is not a stable contract. What should the actual routing representation be?
- **Options considered:** (A) a Markdown table with fixed, validated columns and stable rule identifiers, generating a machine-readable index | (B) structured front matter with a small rules collection | (C) a repository-local generated data file with human-readable generated documentation
- **Decision:** (A), producing a generated `docs/routing.generated.json` from the validated table — same pattern this repo already uses for `docs/index.generated.*`/`specs/*.generated.*`.
- **Rationale:** Reuses an existing, already-trusted pattern (generated index derived from validated source) instead of inventing a new one; keeps the human-readable doc as the single authored source.
- **Consequences:** `task-routing.md`/`change-impact-map.md` gain a fixed-column table (`rule_id | path_glob | doc_ref`) that `tools/docs.mjs validate` checks for shape/uniqueness of `rule_id`; `tools/docs.mjs generate` emits `docs/routing.generated.json`; the context-completeness check (task 05) reads only the generated JSON, never re-parses prose.
- **Date:** 2026-08-04 (refinement pass)
- **Affected artifacts:** `tasks/05-context-completeness-and-routing-precedence.md`, `overview.md`

## D13: Context exceptions require an owner-decision reference

- **Question:** A free-form `context_exception: <reason>` field can silence a completeness warning without proving actual owner approval. What should be required instead?
- **Options considered:** keep free-form reason text | require a reference to a recorded owner decision
- **Decision:** Require a reference: `context_exceptions: [{omitted: <path>, decision: <D-id>, reason: <text>}]`, where `decision` must resolve to an entry in the change's own `owner-decisions.md`.
- **Rationale:** A reason string alone is not evidence of approval; a decision-ID reference is checkable and ties the exception to an auditable record, consistent with how every other gated choice in this workflow is recorded.
- **Consequences:** `validateSpecs` rejects a `context_exceptions` entry whose `decision` doesn't resolve. A context exception is semantic content — it changes what the task is allowed to skip — so it is included in the task-level semantic fingerprint (D7), unlike `status`/`execution.suspension`.
- **Date:** 2026-08-04 (refinement pass)
- **Affected artifacts:** `tasks/06-scope-and-follow-up-mechanisms.md`, `overview.md`

## D14: Mechanical-task approval terminology and semantics

- **Question:** "Auto-approved" is ambiguous — does the task's status change automatically after deterministic validation, or is it merely exempt from the review-file requirement while still going through an explicit approval transition?
- **Decision:** The latter, named precisely: **review-exempt deterministic approval**. `type: mechanical` exempts a task from the review-file/fingerprint-match requirement inside `validateApproval`, but the task still transitions via an explicit `approve` call (idempotent-safe, auditable) — it is never silently marked `approved` as a side effect of something else.
- **Rationale:** Removes the ambiguity the refinement flagged; keeps `approve` as the one place `approved` gets written, matching the skill's existing "single approval gate" rule.
- **Consequences:** Task 07's classifier conditions are unchanged (see `areas/context-and-validation-hardening.md`); it fails closed (falls back to requiring the normal review-then-approve cycle, not a silent block with no path forward) whenever any condition doesn't hold. Every mechanical task's approval is still visible in `change.yaml` and in batch/status output exactly like a normal `approved` task.
- **Date:** 2026-08-04 (refinement pass)
- **Affected artifacts:** `tasks/07-mechanical-task-type.md`

## D15: Follow-up ledger — mutable current-state list, not append-only

- **Question:** The original ledger was described as append-only, but its entries also carry mutable resolution states (`open`/`resolved`/`dismissed`) — a direct contradiction.
- **Decision:** Drop "append-only." `follow-ups.md` is a small, mutable, current-state list — each entry's `status` field is edited in place when resolved or dismissed, not superseded by a new entry.
- **Rationale:** "Append-only" and "has a mutable status field" cannot both be true; the ledger's actual purpose (a small durable record of open items) only needs current-state, not an event history — git already provides the history if ever needed.
- **Consequences:** Task 06 documents valid statuses (`open`/`resolved`/`dismissed`), who may dismiss an item (the owner, or the agent applying an already-approved `AUTO_FIX`-equivalent resolution — never silently by the reviewer that raised it), that dismissal of a `blocking` item requires an explicit owner decision, which severities block task completion vs. batch review vs. finalization, how a `resolver_task` reference is validated (must resolve to a real task id in the same or a named change) and how a stale reference is detected (`validateSpecs` check).
- **Date:** 2026-08-04 (refinement pass)
- **Affected artifacts:** `tasks/06-scope-and-follow-up-mechanisms.md`, `overview.md`
