## D1: Additive two-track migration model with manifest workflow mode

- **Question:** How should Nevo migrate from agent-orchestrated semi-deterministic workflows to a CLI-driven deterministic workflow engine without breaking active specifications or existing agent skills?
- **Options considered:** Big-bang rewrite replacing all lifecycle commands | temporary process-level CLI flag `--deterministic-flow=true` as sole mechanism | additive dual-track engine with manifest-declared workflow mode/version and legacy fallback.
- **Decision:** Adopt an additive dual-track architecture. Specifications declare `workflow: { mode: 'deterministic', version: 1 }` (or `workflow_mode: deterministic`) in `change.yaml`. If omitted, specs default to `mode: legacy`. Existing commands (`start`, `complete`, `verify`, `approve`, `finalize`, `self-check`, `batch-*`) and legacy agent skills continue executing their proven paths unchanged.
- **Rationale:** Prevents breaking active work or making a specification half-legacy and half-deterministic due to varied CLI flags. CLI flags like `--deterministic-flow` are only supported for local testing/development, while the manifest is the long-term source of truth.
- **Consequences:** All deterministic abstractions are built and proven in isolation before any existing agent skill is migrated to depend on them.
- **Date:** 2026-08-18
- **Affected artifacts:** `overview.md`, `change.yaml`, `areas/workflow-schema-and-compatibility.md`, task 01

## D2: Composable action extension model (`check` and `execute`)

- **Question:** How should workflow steps define and invoke lifecycle operations without embedding action-specific business logic into the workflow engine?
- **Options considered:** Hardcoded command switch statements in the engine | plugin scripts invoked via shell | composable `ActionContract` interface exposing non-mutating `check(context)` and fail-closed `execute(inputs, context)` methods.
- **Decision:** Every workflow action implements a standardized `ActionContract`. The workflow engine is decoupled from action internals and orchestrates actions purely through `check` and `execute`.
- **Rationale:** Allows adding or modifying actions (e.g. `commit-and-push`, `verify-task-output`, `format-code`) without modifying core workflow orchestration.
- **Consequences:** Actions own their input definitions, context extraction, and execution logic.
- **Date:** 2026-08-18
- **Affected artifacts:** `areas/composable-actions-and-contracts.md`, tasks 02, 03, 04

## D3: Separation of parameter schema (`requiredInputs`) and runtime facts (`context`)

- **Question:** How should action requirements and runtime state be surfaced to calling agents and human operators?
- **Options considered:** Single unstructured key-value bag | prompt templates generated by the CLI | structured separation between `requiredInputs` (schema) and `context` (runtime facts) with preserved action boundaries.
- **Decision:** An action's `check` returns: (1) `requiredInputs` as a self-describing schema array (specifying parameter name, type, required status, description, and constraints), and (2) `context` providing read-only runtime facts (e.g. changed files, branch state, task affected files). When a step aggregates multiple actions, action boundaries are strictly preserved.
- **Rationale:** Agents can inspect factual context to determine parameters and supply explicit inputs according to schema, eliminating the need to guess parameter semantics or reconstruct rules from markdown instructions.
- **Consequences:** Aggregated checks never collapse multiple actions into an ambiguous flat object.
- **Date:** 2026-08-18
- **Affected artifacts:** `areas/composable-actions-and-contracts.md`, tasks 02, 03, 04

## D4: Fail-closed action execution invariant and explicit file selection for `commit-and-push`

- **Question:** What should happen when an action is executed without required parameters or with invalid parameter values, and how should `commit-and-push` handle uncommitted files?
- **Options considered:** Heuristic guessing/defaulting of missing values and implicit staging of all dirty files | interactive prompt prompting stdin | strict fail-closed rejection with structured precondition errors requiring explicit file selection.
- **Decision:** Execution fails closed immediately. Missing or invalid parameters throw an explicit `PreconditionError` / `CliError`. Specifically, `commit-and-push` requires an explicit file selection (an explicit `include` array, or explicit `include: "*"` with `exclude: [...]`) and must never fall back to committing all dirty files implicitly.
- **Rationale:** Enforces deterministic preconditions: `check` -> inspect context -> collect explicit inputs -> `execute`. Prevents unintended side-effects and accidental dirty-file commits.
- **Consequences:** Reduces silent failures, accidental partial commits, and unintended side effects.
- **Date:** 2026-08-18
- **Affected artifacts:** `areas/composable-actions-and-contracts.md`, `areas/concrete-actions-and-vertical-poc.md`, tasks 02, 04

## D5: First-class deterministic gates with inspection vs verification separation and machine-readable human verification

- **Question:** How should step exit criteria, automated test verification, and human review be modeled without running expensive test suites during read-only inspection?
- **Options considered:** Single `evaluate()` method that runs tests whenever queried | prose instructions telling the agent to "ask user to verify" | dual gate contract separating non-mutating `inspect(context)` from explicit `verify(context)`, plus first-class machine-readable `HumanVerificationGate` (`status: blocked`, `reason: human-verification-required`).
- **Decision:** Gates define two distinct operations: (1) non-mutating `inspect(context)` returning verification target, scope, staleness, and known result without executing commands, and (2) `verify(context)` executing the actual verification action. Human verification is modeled as an explicit machine-readable state (`status: blocked`, `reason: human-verification-required`) that an AI agent cannot self-satisfy.
- **Rationale:** Prevents read-only operations (`status`, `next-step`, `--check`) from triggering slow/expensive test suites, and guarantees that human review cannot be bypassed.
- **Consequences:** Step transitions are gated until exit criteria are verified and human approval is explicitly recorded.
- **Date:** 2026-08-18
- **Affected artifacts:** `areas/deterministic-gates-and-human-verification.md`, task 05

## D7: Configurable declarative workflow definitions across specification classes

- **Question:** How should the deterministic engine accommodate Nevo's multiple specification classes (Standard, Architectural, Small, Exploratory)?
- **Options considered:** Hardcode a single Standard workflow into the engine and defer definitions to Stage 3 | create 4 separate execution engines | introduce a declarative workflow definition schema and loader in this foundation that composes steps, actions, entry/exit gates, and finalize actions per specification class.

## D9: Target agent interaction model — `step start` / `step finish` as the only required primitives

- **Question:** Should the deterministic workflow expose its underlying actions, gates, and transitions directly to the agent, or a smaller compiled surface?
- **Options considered:** Expose `next-step`/`execute-step`/per-action `check`/`execute` as separate agent-facing calls (original Task 06/07 shape) | a minimal two-call contract (`workflow step start`, `workflow step finish`) with the engine compiling everything else internally.
- **Decision:** The normal agent flow is exactly `workflow step start <change> [task]` → bounded work → `workflow step finish <change> [task]`. The runtime resolves the current step from `change`/`task` state without requiring an explicit step id in the common case; explicit step ids remain available for diagnostics/manual override. The agent never discovers or orchestrates individual actions, gates, Git/`gh` commands, or transition rules itself.
- **Rationale:** Nevo owns the process; the agent owns only the bounded work and the semantic inputs the workflow asks for. A chatty, primitive-level protocol reintroduces the same orchestration burden this specification exists to remove.
- **Consequences:** `next-step`/`execute-step` from the original Task 06/07 design are superseded before ever being implemented — `step start`/`step finish` are the real CLI surface; internal step-runner/engine primitives (`checkStep`, `executeStep`, gate `inspect`/`verify`) remain and are composed *underneath* the two-call surface, not exposed as separate agent-facing commands.
- **Clarification — explicit agent vs. operator surface:** This decision governs the *agent*-facing surface only. A distinct *operator*-facing surface exists for human sign-off: `workflow verify-human <change> <task> --confirm` (already described under the gates architecture, D5/C8). This command is never folded into the agent's two calls and is never something the agent workflow itself can invoke to self-satisfy a human gate. When a human-verification exit gate is unmet, `workflow step finish`/`step finish --check` reports it the same way it reports any other unmet exit gate — via that gate's `inspect()` status in the finish-planning payload (`gates: [...]`, `blockers: [...]`) — it never attempts to perform, wait for, or bypass the confirmation itself. Task 07's vertical PoC must exercise the operator command as its own explicit step in the terminal-only flow, distinct from both agent calls.
- **Date:** 2026-09-07
- **Affected artifacts:** `overview.md`, `areas/workflow-engine-and-next-step.md`, `areas/concrete-actions-and-vertical-poc.md`, tasks 06, 07

## D10: Compiled `StepContext` at `step start`

- **Question:** What must `step start` return so the agent can begin bounded work without further workflow discovery?
- **Options considered:** Return only the current step id/status, leaving the agent to call `checkStep`/inspect gates itself | return a compiled `StepContext` aggregating everything the agent needs in one call.
- **Decision:** `step start` returns a compiled `StepContext`: current step id, task/spec identity, workflow state, step instructions/behavior, entry state and blockers, available/expected work, factual runtime context (including source-control context when enabled), the finish contract (aggregated `requiredInputs` from finalize actions, e.g. `commit.title` required / `commit.message` optional), and next-step guidance where meaningful. The agent must not need to inspect individual actions to discover their schemas — the step orchestration layer aggregates action/gate contracts into this one step-level contract, reusing `WorkflowEngine.checkStep`'s aggregation (Task 03) rather than re-implementing it.
- **Rationale:** Matches D9 — the agent begins work from one call's output, not a sequence of discovery calls.
- **Consequences:** The finish contract shape (`requiredInputs` aggregated across finalize actions) must be computable *before* any work happens, and must match exactly what `step finish`/`step finish --check` later reports — the two are the same aggregation, evaluated at two different times, not two different implementations.
- **Date:** 2026-09-07
- **Affected artifacts:** `overview.md`, `areas/workflow-engine-and-next-step.md`, task 06

## D11: Non-mutating finish planning, and `step finish` itself returns `input-required` without partial mutation

- **Question:** How does the agent discover what `step finish` still needs, and does discovering it require a separate call in the happy path?
- **Options considered:** Require a mandatory `step finish --check` before every real `step finish` | make `--check` optional/diagnostic, and have `step finish` itself return a structured `input-required` result (aggregating current changed files, staged/untracked state, relevant commits, branch/HEAD, push status, planned operations, and missing inputs) instead of partially mutating when inputs are missing.
- **Decision:** `step finish --check` (or an equivalent dry-run form) is available for inspection/automation and is strictly non-mutating (same invariant as the existing action `check(context)` / gate `inspect(config, context)`, C2). It is never mandatory: calling `step finish` directly with all required inputs completes normally in one call; calling it with missing inputs returns `status: "input-required"` plus the same factual planning payload `--check` would have returned, and performs zero mutation.
- **Rationale:** Preserves the low-call happy path (`step start` → work → `step finish`) from D9 while still giving the agent a safe way to discover missing inputs without guessing or repeating side effects.
- **Consequences:** The `input-required` code path and the `--check` code path must share one planning implementation — they differ only in whether the caller intended to also execute when inputs turn out to be complete.
- **Date:** 2026-09-07
- **Affected artifacts:** `overview.md`, `areas/workflow-engine-and-next-step.md`, task 06

## D12: Source control as a workflow capability — local Git vs. remote GitHub provider, reusing existing infrastructure

- **Question:** How should Task 04 evolve from a single `commit-and-push` action into the minimal source-control capability the deterministic workflow needs, without building a general VCS abstraction?
- **Options considered:** Keep `commit-and-push` as the only source-control surface, with push-confirmation logic embedded in it | introduce a full pluggable VCS provider framework supporting arbitrary future backends now | split into two conceptual layers — a local Git capability (repo/worktree state, commit, push, and reconciliation facts such as "is this SHA already on the configured remote branch") and a separately configured remote provider (currently `github` only), both built on the repository's existing `tools/lib/git.mjs` and `tools/lib/github.mjs` rather than new abstractions.
- **Decision:** Adopt the two-layer split. `tools/lib/git.mjs` (already used by the legacy `finalize`/`archive` paths for `commitAll`/`push`) is extended, not replaced, with whatever reconciliation primitive Task 04 needs (e.g. "is commit X reachable from `origin/<branch>`"). `tools/lib/github.mjs` (already the repository's one GitHub integration, used today by PR/review tooling) remains the sole GitHub abstraction — Task 04 does not create a second one. Configuration takes the shape:
  ```yaml
  sourceControl:
    enabled: true
    push: true
    remote:
      enabled: true
      provider: github
  ```
  The exact schema *location* (workflow definition file vs. per-change manifest) remains a Task 04 implementation detail; the field semantics above are fixed here and are not open to task-level reinterpretation (see the correction below for why).
- **Rationale:** Matches specification requirement 3 exactly: reuse existing Git/GitHub infrastructure, keep a clean two-layer capability boundary, and avoid building a universal VCS framework this foundation does not need. GitLab or any other provider stays unimplemented — only the boundary that could later accept one is established.
- **Consequences:** GitHub-provider-specific *mutating* operations (e.g. opening a PR) are still out of scope for this action — Task 04 only needs the config boundary plus local Git commit/push/reconciliation, since ordinary step finalization never requires a GitHub write beyond what `push` already achieves.
- **Correction — flattened configuration, resolved case table:** The original sketch nested `git: { enabled, push }` under `sourceControl`, leaving the relationship between `sourceControl.enabled` and `git.enabled` ambiguous — no real use case needs them independent (there is no scenario where source control is "enabled" but its local-Git layer isn't). `git.enabled` is removed; `push` moves to a direct child of `sourceControl` (schema above). The four cases this must make unambiguous:

  | Case | Configuration | Meaning |
  |---|---|---|
  | No automation | `sourceControl.enabled: false` | No commit, no push, no remote operation; the commit/push action contributes no `requiredInputs` to the step's finish contract. |
  | Local commit, no push | `enabled: true, push: false` | Commits are created; nothing is pushed. `remote.enabled` must be `false`/absent — meaningless without a push. |
  | Commit + ordinary push, no provider | `enabled: true, push: true, remote.enabled: false` | Plain Git push; "is this pushed" reconciliation uses pure Git (`ls-remote`/`rev-list` via the Task 04 primitive) — no GitHub API call involved. |
  | Commit + push + GitHub provider | `enabled: true, push: true, remote: { enabled: true, provider: github }` | Same as above, plus the GitHub-provider-specific capability boundary is available for future provider-specific operations — this foundation adds no additional mutating operation beyond ordinary push. |

  `remote.enabled: true` with `push: false` is an invalid, contradictory configuration.
- **Refinement — fail-closed only, no normalization:** The prior wording allowed either rejecting this configuration or silently normalizing it to `remote.enabled: false`. That choice is now resolved: `remote.enabled: true` with `sourceControl.push: false` **must** produce a configuration validation error — it is never silently normalized. Normalizing would mean the runtime accepted and reinterpreted a configuration the caller never actually specified, which is exactly the kind of silent, ambiguity-hiding behavior C6's fail-closed principle already forbids for action inputs; the same standard applies here to configuration.
- **Date:** 2026-09-07
- **Affected artifacts:** `overview.md` (non-goals, constraints), `areas/concrete-actions-and-vertical-poc.md`, task 04 (renamed)

## D13: Finalize ordering invariant — the progress commit includes task/spec completion state

- **Question:** In what order must finalize operations run so that a completed step's commit reflects both the agent's work and Nevo's own bookkeeping?
- **Options considered:** Commit the agent's work first, update task/spec status afterward in a second, separate commit | update task/spec completion state, then commit both the implementation and the metadata update together, then push.
- **Decision:** The externally visible order for a task-completing step is: validate supplied inputs → verify required gates → perform/update task/spec completion state → commit the resulting implementation plus Nevo metadata/status changes together → push when configured → confirm remote state → persist/complete the workflow transition → return completed state and next step. Internal sequencing may vary for failure recovery (D14), but this order is the invariant callers can rely on.
- **Rationale:** Avoids ever leaving task metadata dirty immediately after a successful finalize — a real failure mode when metadata and implementation are committed separately (a crash between the two commits leaves an inconsistent repo state).
- **Consequences:** The source-control finalize action(s) (Task 04) must be sequenced *after* task/spec status mutation in the finish operation's stage list (Task 06), not before it and not as a caller-supplied ordering choice. The final `persist/complete the workflow transition` step is a runtime-record/response-shaping operation only — it never writes `change.yaml` again, since the task/spec status change already happened and was already committed by the earlier steps. Reading "transition" as a second manifest write would reintroduce the exact "left dirty after finalize" failure this decision exists to prevent (see C17).
- **Date:** 2026-09-07
- **Affected artifacts:** `overview.md`, `areas/concrete-actions-and-vertical-poc.md`, tasks 04, 06

## D14: Durable, resumable finish execution — operation state model and reconciliation

- **Question:** How does a multi-stage finish operation survive a crash, timeout, or lost response without either repeating a completed side effect or getting stuck?
- **Options considered:** No durability — a retried `step finish` simply re-runs every finalize action from scratch | a full distributed-transaction/saga framework | a minimal durable operation record: a stable `operationId`, a fixed per-stage status vocabulary (`pending`/`running`/`completed`/`failed`/`unknown`), and reconciliation logic that inspects real state before deciding what still needs to run.
- **Decision:** Adopt the minimal durable operation record — but, per the correction below, it is **workflow execution/runtime state**, persisted in Nevo's local runtime storage, never inside Git-tracked `change.yaml`:
  ```json
  {
    "operationId": "...",
    "change": "deterministic-workflow-foundation",
    "task": "06-step-orchestration-and-next-step-service",
    "step": "implementation",
    "status": "running",
    "resolvedInputs": {
      "commit.title": "...",
      "commit.message": "...",
      "include": ["..."],
      "exclude": []
    },
    "operations": [
      { "id": "verify-gates", "status": "completed" },
      { "id": "update-task", "status": "completed", "intent": { "fromState": "in-implementation", "toState": "implemented" } },
      { "id": "commit", "status": "completed", "intent": { "preCommitHead": "def456" }, "result": { "sha": "abc123" } },
      { "id": "push", "status": "unknown", "result": { "remote": "origin", "branch": "feature/foo", "expectedSha": "abc123" } },
      { "id": "transition", "status": "pending" }
    ]
  }
  ```
  On retry, Nevo loads the existing record, treats `completed` stages as done, and reconciles any `unknown` stage against real external state before deciding whether it is actually `completed` or still `pending` — e.g. a `push` left `unknown` after a crash is reconciled by checking (via the Task 04 Git reconciliation primitive from D12) whether the recorded commit SHA is already present on the expected remote branch. It never re-creates a commit that already exists. A repeated `step finish` after the operation record shows full success returns the already-completed result and current next step rather than repeating finalize actions.
- **Rationale:** Matches specification requirement 6 exactly — a foundation-level resumability invariant, not a claim of exactly-once distributed semantics. `unknown` is the state that makes reconciliation meaningful: it marks an external side effect whose outcome Nevo did not confirm, as distinct from `failed` (confirmed not to have happened) or `completed` (confirmed to have happened).
- **Refinement — closing the crash window for a stage left `running`:** The original decision defined reconciliation for `unknown`, but left a real gap: a mutating stage can crash *after* its side effect happens and *before* the record is updated to `completed`, leaving it recorded as `running` — a state distinct from both "confirmed not started" (`pending`) and "confirmed uncertain" (`unknown`). **`running` found on recovery is never trusted at face value and never blindly reset to `pending`** — it is *always* reconciled first, exactly like `unknown`, using persisted pre-mutation intent plus real current state:
  - **`update-task`**: before mutating, persist `intent: { fromState, toState }` (the task/spec state transition about to happen). On recovery: current tracked state `== toState` → the write happened, mark `completed`; current tracked state `== fromState` → it never happened, safe to (re)execute; anything else → ambiguous, never guess — report the stage as `unknown` and return a machine-readable reconciliation-required response instead of proceeding.
  - **`commit`**: before running `git commit`, persist `intent: { preCommitHead }` (the current HEAD SHA) — the exact file selection and commit title/message needed to reconcile are already covered by `resolvedInputs` below, not duplicated here. On recovery: current HEAD `== preCommitHead` → the commit never happened, safe to (re)execute; current HEAD differs → call `tools/lib/git.mjs`'s `getCommitInfo(root, 'HEAD')` (Task 04's second reconciliation primitive, alongside the push-presence one) to read the current HEAD commit's `parentSha`/`subject`; `parentSha === preCommitHead` and `subject` matching the persisted `resolvedInputs['commit.title']` together prove HEAD is this operation's own commit — recover its SHA and mark `completed`; otherwise report `unknown` and block for reconciliation — **never create a second commit merely because the stage still says `running`.**
  - **`push`**: unchanged model (D15) — `expectedSha` is itself the pre-push intent, already persisted before the `git push` call as part of moving the stage to `running`/`unknown`. A recovered `running` push is reconciled exactly like an `unknown` one — no separate handling needed.
  - **`transition`**: remains runtime-only and idempotent — it introduces no tracked-metadata mutation of its own (see D13's consequence), so there is nothing to reconcile beyond re-deriving the next-step response.
  - This reuses the existing five-value vocabulary (`pending`/`running`/`completed`/`failed`/`unknown`) — reconciliation is a *process* every mutating stage goes through when found `running` on recovery, not a sixth status value.
- **Refinement — resolved finish inputs are persisted once, before the first mutation:** `resolvedInputs` (the caller's validated `commit.title`/`commit.message`/`include`/`exclude`, or the applicable subset) is written into the record once, before `update-task` (the first mutating stage) executes. A resumed `workflow step finish` for an existing in-flight operation uses these persisted inputs — the agent/operator is never required to rediscover or resupply them after a crash, and calling `step finish` with no inputs at all correctly resumes. If a resumed call *does* supply inputs that differ from what's already persisted for that `operationId`, this is a deterministic conflict, reported as such — Nevo never silently substitutes the new values for the operation's already-established intent. Supplying the same values again is a harmless no-op.
- **Correction — moved out of Git-tracked `change.yaml`:** The original design persisted this record under an `execution.finish_operation` manifest field inside the task's `change.yaml` entry, alongside `execution.suspension`. This created a circular consistency problem: a commit cannot contain its own resulting SHA, so the `commit` stage's result could never be written into the very commit it describes; and every post-commit bookkeeping write (recording `push`/`transition` completion) would leave the worktree dirty again immediately after a clean finalize — directly undermining the "not left dirty" invariant this record exists to protect (see C17). The fix: this durable finish-operation record is workflow *execution/runtime* state, not Git-tracked domain/specification state, and now lives in Nevo's local runtime storage under `.nevo-ai-local/workflow-operations/<change>/<task>.json` — the same git-ignored, project-local storage convention already established by `tools/dashboard/server/ai/sessions/binding-service.mjs` (one JSON file per key, written atomically via temp-file-then-rename). Task 06 implements its own small, minimal read/write helper following that same on-disk convention — it does **not** add a dependency from `tools/specs/workflow/` on `tools/dashboard/`; the convention is reused, not the code. `change.yaml`'s existing `execution.suspension` block is unaffected by this correction and remains exactly as documented in `docs/ai/specification-workflow.md` — it is a distinct, task-lifecycle-level concept (why the *last attempted action* stopped) that this new, more granular, finish-sequence-specific runtime record does not replace or merge with. No manifest field named `execution.finish_operation` exists anywhere in the current design — that name is retained here only as the historical label for what this correction removed.
- **Consequences:** No manifest schema changes are needed in `tools/specs/validation.mjs` for this record — it is not part of `change.yaml` at all, so Task 01's already-verified schema/validator work is untouched by Task 06. Task 06 owns the small local-storage helper instead of a manifest schema addition.
- **Date:** 2026-09-07
- **Affected artifacts:** `overview.md`, `areas/workflow-engine-and-next-step.md`, tasks 06, 07

## D15: Push completion represents achieved state, not command invocation

- **Question:** What must be persisted about a push so Nevo can answer, deterministically and later, "has the expected commit actually reached the remote?"
- **Options considered:** Persist only "push succeeded: true/false" at the moment the push command returned | persist the specific expected commit SHA alongside the push's remote/branch/status, so the claim can be re-verified against current remote state at any later time (not just trusted from the original command's exit code).
- **Decision:** Persist `{ commit: { sha, status }, push: { remote, branch, expectedSha, status } }` as part of the finish operation's `commit`/`push` stage results (D14). `expectedSha` is what makes reconciliation (D14) and any later "is this pushed" query answerable without re-trusting a possibly-stale in-memory result.
- **Rationale:** Matches specification requirement 7. This is also exactly what the reconciliation step in D14 needs as its input.
- **Consequences:** None beyond D14 — this decision defines the payload shape D14's `push` stage carries.
- **Date:** 2026-09-07
- **Affected artifacts:** `overview.md`, task 04, task 06

## D16: Legacy lifecycle stays operational, explicitly marked superseded

- **Question:** Should any legacy lifecycle command be removed or altered as part of establishing the deterministic step lifecycle?

## D18: Persisted workflow-step progress is new, Git-tracked task state, distinct from task lifecycle `status` — **approved by owner 2026-09-08**

- **Question:** Tasks 01-07 proved exactly one workflow step (`implementation`). A real multi-step workflow definition (e.g. `implementation -> review -> quality -> human-approval -> complete`) needs the engine to know, deterministically and durably, which of several steps a given task is currently on. Is the existing task lifecycle `status` (`draft`/`approved`/`in-implementation`/`implemented`/`verified`) sufficient to represent that, or does a distinct, separately-persisted workflow-step-progress state need to exist? If a new state is needed, where does it live — Git-tracked `change.yaml` (like `status` itself) or Nevo's local runtime storage (like the finish-operation record, D14)?
- **Options considered:**
  1. Overload existing task `status` values as step markers (e.g. invent a status per intermediate step). Rejected outright per the review that triggered this decision: `status` already carries independent, legacy-relied-upon meaning (dependency-graph satisfaction via `DEPENDENCY_SATISFYING_STATUSES`, human-approval gating via `approve`, archival eligibility) that has nothing to do with which step of a *deterministic* workflow a task is on; conflating the two would make `status` mean two unrelated things depending on `workflow.mode`, and would break the moment a specification needed both a real multi-step workflow *and* today's status-driven dependency/approval semantics at the same time.
  2. A distinct per-task field, persisted as **runtime-only local state** (`.nevo-ai-local/workflow-progress/<change>/<task>.json`), parallel to the finish-operation record (D14).
  3. A distinct per-task field, persisted as **Git-tracked `change.yaml` state** (e.g. `task.workflow_progress: { current_step, history: [...] }`), committed in the same progress commit as everything else (C14).
- **Decision — Option 3, approved:** Git-tracked `workflow_progress` on the task entry. The owner's own stated rationale for approving it: it is long-lived workflow/domain progress, unlike the finish-operation record's transient, single-call crash-recovery state (D14) — matching the reasoning already recorded below. The `update-task` finalize stage (Task 06) already writes to `change.yaml` and commits that write together with the implementation (C14) — extending it to also write `workflow_progress` is a small, consistent generalization of a mechanism this specification already built and verified, not a new one.
  - This was a persistence-ownership choice (`AGENTS.md`'s owner-approval-required list) and was presented, not silently decided — the owner confirmed Option 3 explicitly on 2026-09-08. Tasks 08-12 are written assuming it.
- **Consequences:** `tools/specs/validation.mjs` gains a new optional `workflow_progress` schema block (Task 08) — the first schema growth to `change.yaml` since D1, and the first Git-tracked field introduced specifically for the deterministic engine (everything so far was either manifest-level mode/version or explicitly kept out of `change.yaml`, per D14).
- **Date:** 2026-09-08
- **Affected artifacts:** `overview.md`, `areas/multi-step-workflow-orchestration.md`, task 08

## D19: Step transitions resolve against the workflow definition's own step names; a non-matching target is the terminal signal

- **Question:** Today's only workflow definition has one step whose transition is `{ to: verified }` — `verified` is a task lifecycle status, not a step name, and `resolveCurrentStepName` never needed to distinguish the two. A real multi-step definition needs `to` to sometimes mean "advance to this other step" and sometimes mean "this workflow is done, set the task's terminal lifecycle status" — how does the engine tell which, without a hardcoded list of step names or status names?
- **Options considered:** Add an explicit `terminal: true` flag to a transition entry, so authors mark the last step outright | resolve `to` against the current definition's own `steps` map keys first — a match means "advance to that step" (workflow-internal), no match means "this is a terminal lifecycle transition" (workflow-external, i.e. a task-status value).
- **Decision:** Resolve against the definition's own `steps` keys. A transition's `to` value that names another declared step in the same definition advances `workflow_progress.current_step` to it, leaving task `status` untouched; a `to` value that names no declared step is the terminal case — it is written to task `status` exactly as today, and `workflow_progress` is cleared/finalized. This requires no new schema field and is fully backward compatible: today's only definition (`implementation -> { to: verified }`) already satisfies it, since `verified` has never been a step name.
- **Rationale:** Avoids inventing a second way to say "this is the end" (a boolean flag that could disagree with the `to` value) and avoids hardcoding either step names or status names into the engine — the workflow definition's own structure is the only input needed. This is exactly the "the workflow definition decides what happens next" principle this specification's Goal already states, applied to the transition-target question specifically.
- **Consequences:** A workflow definition author must not reuse a real step's name as if it were also a valid terminal task-status value (e.g. a step literally named `verified` would make that transition target ambiguous with intent) — Task 08's schema validation must reject that collision at load time rather than let it silently resolve as "advance to step `verified`" when a terminal `status: verified` was actually meant.
- **Date:** 2026-09-08
- **Affected artifacts:** `overview.md`, `areas/multi-step-workflow-orchestration.md`, task 08

## D20: Fail-closed workflow definition resolution — an unregistered action/gate reference is a configuration error, never a silent no-op

- **Question:** `.nevo-ai/workflows/standard.yaml` declares `finalize: [verify-task-output, commit-and-push]`, but no `ActionContract` named `verify-task-output` was ever registered (only `commit-and-push`, Task 04). `step-context.mjs`'s `aggregateFinalizeCheck` was written (Task 06) to filter the finalize list down to already-registered actions before aggregating, specifically to tolerate this gap. Is that tolerance acceptable long-term, or does it violate this specification's own fail-closed principle (C6)?
- **Options considered:** Keep the tolerant filter — a configured-but-unregistered action silently drops out of execution | make it a fail-closed configuration/definition error — the workflow cannot run at all until every declared action id and gate reference is registered.
- **Decision:** Fail closed. A workflow definition (or a step within one) that references an action id with no registered `ActionContract`, or a gate configuration whose type has no registered `GateContract`, must produce an explicit, reported error — never a workflow that silently runs with fewer steps of work than declared. The tolerant filter (`step-context.mjs`'s `registeredFinalizeActions`) introduced during Task 06 is removed. `verify-task-output` is removed from `.nevo-ai/workflows/standard.yaml`'s `finalize` list rather than left as a permanently-silently-ignored placeholder; if a real output-verification action is ever needed, it is implemented and re-added as a genuine, registered action in a future task — never reintroduced as an unregistered reference.
- **Rationale:** C6 already established this exact standard for action *inputs* ("execution must fail closed... rather than guessing or heuristic defaulting"); a configured-but-unimplemented action or gate *reference* is the same failure class one level up — the workflow silently became a different, smaller workflow than what was declared, which is precisely what this specification exists to prevent agents from having to guess around.
- **Consequences:** `tools/specs/workflow/definitions/loader.mjs`'s `loadWorkflowDefinition` must be called with `knownActions` populated from the real `ActionRegistry` (which requires the action-registration side effect, `actions/index.mjs`, to have already run) so an unregistered action reference fails at load time, not silently at aggregation time. Gate types were already validated at schema-load time (`KNOWN_GATE_TYPES`) — this decision closes the one remaining silent-degradation path, which was action-side only.
- **Date:** 2026-09-08
- **Affected artifacts:** `overview.md`, `areas/multi-step-workflow-orchestration.md`, `.nevo-ai/workflows/standard.yaml`, task 09

## D23: Finish-operation identity is step-aware — a completed record from one step must never short-circuit another

- **Question:** The durable finish-operation record (D14) is keyed only by `<change>/<task>.json`. Once a real multi-step workflow exists (D18/D19), step A's finish leaves that file `completed`. When step B later finishes, `planFinish`/`finishStep` would load the *same* file, see `status: completed`, and wrongly report B as already done without ever running B's finalize sequence. How should operation identity account for which step it belongs to?
- **Options considered:** Keep one record per task and reset/overwrite it when advancing to a new step (destroys the completed evidence for the previous step, and a crash mid-reset could lose both). | Keep one record per task but add a `step` field inside it, checked before trusting `status: completed` (still one mutable file — a step-B write could still race with lingering step-A intent fields not fully cleared). | Make the record identity itself step-aware: one file per `(change, task, step)`.
- **Decision:** One file per `(change, task, step)` — `.nevo-ai-local/workflow-operations/<change>/<task>/<step>.json` (was `<change>/<task>.json`). The invariant this establishes:
  - a finish operation belongs to exactly one workflow step, identified by its file path;
  - loading/checking "is this already done" only ever reads the file for the *current* resolved step — a previous step's `completed` record is a different file and is structurally unreachable from the current step's resolution path;
  - retrying the same step re-resolves the same path and therefore the same `operationId`/record, resuming exactly as today (D14 unchanged for the single-step case);
  - advancing to a different step resolves a different path — nothing to load, so a fresh operation record is created for it;
  - the previous step's completed file is never deleted or overwritten by a later step's operation — it remains on disk as history (satisfying "preserve previous operation history where useful rather than silently overwriting evidence" without adding a new consolidated-history mechanism; each step's own file *is* its history).
- **Rationale:** This is the smallest change that makes the invariant structurally true rather than logically asserted — no new field needs to be checked-and-trusted before every use of `status: completed`; the file system path itself is the scope boundary. It also composes cleanly with D19: resolving the current step already happens before `planFinish`/`finishStep` touch the operation record, so the step name is always available to compute the path.
- **Consequences:** `loadOperationRecord`/`saveOperationRecord` (`finish-operation.mjs`) gain a `step` parameter; every caller (Task 06's own `planFinish`/`finishStep`, Task 07's CLI wiring, all existing tests) updates its call sites accordingly. This is a pre-implementation correction to Task 08's own design, not a change to anything Task 06/07 already shipped and verified (the D14 record format and the single-step directory layout were never load-bearing outside Task 06/07's own module).
- **Date:** 2026-09-08
- **Affected artifacts:** `overview.md`, `areas/multi-step-workflow-orchestration.md`, task 08

## D24: Human-verification sign-off identity is scoped to the exact configured step/gate, not just the task

- **Question:** The file-backed `FileHumanVerificationStore` (Task 07) persists one confirmation per `(change, task)` with a fixed `{scope: 'task', targetId: task.id, role: 'owner'}` shape. Once a workflow can have several independently-configured `HumanVerificationGate`s across different steps (e.g. a "review" step's human gate and a "human-approval" step's human gate), that one confirmation-per-task model would let confirming *any* human gate on a task silently satisfy *every* human gate on that task, including ones the operator never actually reviewed. How should sign-off identity be scoped so a confirmation only ever satisfies the exact gate it was given for?
- **Options considered:** Keep the existing task-scoped confirmation (accept that any human gate on a task shares one sign-off) | scope by `(change, task, step)` only (distinguishes steps but not multiple human gates within the same step) | scope by `(change, task, step, gate identity, required role)` — the full configured identity.
- **Decision:** Scope by the full tuple: `change` + `task` + `step` + gate identity (`gateDisplayId`, already computed for exit-gate display — e.g. `human-review`, or a gate's explicit `id` when configured) + `requiredRole` (the gate's configured `role`, default `owner`). Storage path: `.nevo-ai-local/human-verifications/<change>/<task>/<step>/<gate-id>.json`. The public operator command remains `workflow verify-human <change> <task> --confirm`, auto-resolving the *current* step the same way `step start`/`step finish` do; if that step has more than one unmet human gate (an edge case — most steps have at most one), the command requires an explicit `--gate <id>` to disambiguate rather than guessing which one the operator means. `HumanVerificationGate`'s own shared contract (`inspect`/`verify`, Task 05, unchanged) already accepts a `scope`/`role` per gate config — this decision only changes how *our* CLI-facing store keys its own persisted file, not the shared gate abstraction.
- **Rationale:** A sign-off that can silently satisfy a gate the operator never looked at is a real correctness gap, not just a naming inconvenience — it would make "human verification cannot be bypassed" (C8) false for any workflow with more than one human gate. Keying by the full configured identity is the direct fix and costs nothing extra at confirm time, since `verify-human` already needs to resolve the current step to report a useful confirmation.
- **Consequences:** Preserves every existing invariant: the agent still has no code path to write this file (`step start`/`step finish` never call `.confirm()`); `verify-human` remains the one, separate operator command; the record remains file-backed and durable across CLI process invocations. `FileHumanVerificationStore`'s constructor and file-path function gain `step`/`gateId` parameters.
- **Date:** 2026-09-08
- **Affected artifacts:** `overview.md`, `areas/multi-step-workflow-orchestration.md`, task 08

## D25: Workflow steps declare a structured, declarative behavior contract — not engine-generated prose

- **Question:** `StepContext` (D22, Task 11) surfaces task-level `allowed_paths`/doc hints, but a multi-step workflow also needs to tell the agent what *this specific step* expects — an "implementation" step and a "review" step bound the same task differently, and the agent must learn that from the workflow definition, never from hardcoded knowledge of step names inside the engine. What shape should this take?
- **Options considered:** Let the engine synthesize step-specific instructions at runtime from the step's gate/action configuration (implicit, and reintroduces exactly the kind of engine-side prose-generation this specification's D22 already ruled out) | add a structured, author-provided behavior contract to the workflow-definition schema itself — declarative data the definition author writes once, that `step start` surfaces verbatim.
- **Decision:** Extend the per-step schema with three optional, structured fields: `purpose` (a short string — the step's own stated intent, e.g. "Implement the bounded work within allowed_paths."), `expectedWork` (a short structured description of what "done" looks like for this step, distinct from the task-level `allowed_paths` D22 already surfaces), and `hints` (an array of structured references — `{ type: 'doc' | 'skill' | 'file', ref: string }` — pointing at existing docs/skills/files, never inline prose essays). All three are authored once, by whoever writes the workflow definition YAML (Task 10 for Standard) — never generated by engine code. `StepContext.stepContract` (or equivalent field name chosen at implementation time) carries whichever of these the current step declares, alongside the task-level fields D22 already added.
- **Rationale:** This is the same principle D22 already established (deterministic, sourced data over generated prose) applied one level down — to the *step*, not just the *task*. It is also exactly what lets a "review" step and an "implementation" step present differently to the agent without the agent (or the engine) needing to special-case either name.
- **Consequences:** Schema support for these fields (validation only — accept/validate, not consume) is Task 08's responsibility, since Task 08 already owns the definition-schema changes for D18/D19/D26/D27; authoring real content for Standard's steps is Task 10's; wiring the configured contract into `StepContext` (combined with the task-level fields) is Task 11's — matching the division the owner specified.
- **Date:** 2026-09-08
- **Affected artifacts:** `overview.md`, `areas/multi-step-workflow-orchestration.md`, tasks 08, 10, 11

## D26: Fail-closed workflow-definition version compatibility

- **Question:** `resolveWorkflowMode(change)` returns `change.workflow.version`; the loaded definition (`normalizeWorkflowDefinition`) carries its own `version` field. Nothing today compares the two. A task can sit at `workflow_progress.current_step` for a long time (D18) — if the definition it was progressing through is later changed to an incompatible new version (different steps, renamed transitions), what should happen the next time that task's `step start`/`step finish` runs?
- **Options considered:** Ignore the mismatch and continue resolving against whatever definition is currently on disk (silently risks resolving a `current_step`/transition that no longer means what it meant when the task started, or no longer exists at all) | build versioned migration/compatibility infrastructure now (definition-version-to-version upgrade paths) | fail closed: reject with an explicit error the moment `change.workflow.version` doesn't match the loaded definition's own `version`.
- **Decision:** Fail closed, nothing more. Every `workflow step start`/`step finish` call (via the same runtime-resolution path that already loads both the manifest's declared version and the definition file) asserts `change.workflow.version === definition.version` before doing anything else; a mismatch is an explicit `WorkflowDefinitionError` naming both versions, not a silent continuation against a possibly-incompatible definition. No migration tooling, no multi-version support, no speculative compatibility matrix — this is a per-call guard, not a framework.
- **Rationale:** Matches this specification's own fail-closed standard (C6/C20) applied to definition *versioning* — the failure mode being prevented (a long-lived task silently resolving against a definition that changed underneath it) is exactly the kind of silent, ambiguity-hiding behavior this specification exists to eliminate, and the fix is cheap: one equality check per call, already have both values in hand.
- **Consequences:** A workflow definition author who makes an incompatible change must bump `version` in both the definition file and any in-flight change's `workflow.version` deliberately — there is no automatic path, by design; this is acceptable because deterministic-mode changes are new and few, not because it would scale to many.
- **Date:** 2026-09-08
- **Affected artifacts:** `overview.md`, `areas/multi-step-workflow-orchestration.md`, task 08

## D27: Exactly one transition per step, and an explicit (optional, defaulting) `entryStep` field

- **Question:** Two related schema-precision gaps: (1) `transitions` is schema-shaped as an array, but every code path that reads it (`nextStepGuidance`, `ensureTransition`, D19's resolution) only ever looks at index 0 — a second declared entry is silently ignored, which is exactly the kind of silent degradation D20 already ruled out for actions/gates. (2) the workflow's entry point (which step a fresh task starts on) is today an implicit convention — "the first key in the `steps` YAML mapping" — never a named, validated field.
- **Options considered, transitions:** Support real conditional/multiple transitions with some deterministic selection rule now | require exactly one transition per step, rejecting zero or more than one at validation time.
- **Decision, transitions:** Require exactly one transition per step (every step, not a "non-terminal" subset — see the note below on why that distinction doesn't actually exist at schema time). `validateWorkflowDefinition` (`definitions/schema.mjs`) rejects a step declaring zero or more than one `transitions` entries. This makes today's `transitions[0]` access provably safe (there is never an index 1) instead of merely-so-far-unexercised. Conditional/multiple transitions are explicitly deferred — not designed, not stubbed — until a real use case demands them.
- **Note on "non-terminal":** there is no separate schema shape for a terminal vs. non-terminal step — D19 already establishes that "terminal" is *derived*, at resolution time, from whether a step's one transition's `to` value happens to match another declared step name or not. So "exactly one transition per step" is the complete rule; no step is exempt.
- **Options considered, entry step:** Keep the implicit "first YAML key" convention | add an explicit, optional `entryStep: <name>` field at the definition's top level, defaulting to the first declared key when omitted (so today's unmodified `standard.yaml` keeps behaving identically).
- **Decision, entry step:** Add `entryStep` as an **optional** top-level definition field. When present, it must name a real declared step and is used as the entry point for a task with no `workflow_progress` yet; when absent, the first declared `steps` key is used, exactly as today — this keeps Task 08's own non-regression requirement (today's unmodified `standard.yaml` must keep behaving identically) trivially true. Task 10's new multi-step Standard definition must set `entryStep` explicitly — there is no excuse for a freshly-authored multi-step definition to rely on implicit ordering.
- **Rationale:** Both changes remove a silent-degradation path (an ignored second transition; an unnamed, easy-to-misread-on-reordering entry point) for the same cost D20 already paid to remove the unregistered-action one — an explicit validation error instead of quietly-different behavior. Making `entryStep` optional-with-safe-default (rather than mandatory) avoids forcing a schema-compatibility break on the one real definition that exists today, while still giving new multi-step definitions (Task 10) an explicit, unambiguous way to state it.
- **Consequences:** A future decision to support real multiple/conditional transitions is not foreclosed — it would be a new, additive schema shape (e.g. a `conditions` field alongside a still-single default `to`), not a reinterpretation of today's array-of-one.
- **Date:** 2026-09-08
- **Affected artifacts:** `overview.md`, `areas/multi-step-workflow-orchestration.md`, tasks 08, 10
